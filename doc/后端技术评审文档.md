## 2. 用户安全认证方案

### 2.1 原则（对齐 openspec `shared.security`）

| 项 | 要求 |
|----|------|
| 传输 | 全站 **HTTPS**，禁止明文凭证在非 TLS 信道传递。 |
| 密码 | **仅以契约为准**：客户端调用 **`GET /v1/auth/password-params`** 取得 **`pepper` / `formulaVersion`**；按 **`openspec/specs/README.md`**（**formulaVersion = 1**）计算 **`passwordPrehash`**（64 位小写十六进制）；**`POST /v1/auth/register`、`POST /v1/auth/login`** 请求体 **仅传 `passwordPrehash`**，不传明文口令。服务端对 **`passwordPrehash`** 做 **BCrypt/Argon2** 存入 **`user.password_hash`**，禁止明文或可逆存储；日志不落 **`passwordPrehash`**。 |
| 会话凭证 | **Session 放于 HTTPOnly、Secure、SameSite 的 Cookie**，**禁止**将长期凭证放入 LocalStorage；若采用 JWT，仍建议短效 + HTTPOnly Cookie 承载或严格防 XSS。 |
| CSRF | 基于 Cookie 的会话对 **变更类操作**（POST/PUT/PATCH/DELETE）使用 **CSRF Token** 或 **SameSite=Lax/Strict** 策略，与前端 `withCredentials` 一致。 |
| 防枚举 | 登录失败对客户端统一文案（不明确区分「用户不存在」与「密码错误」）；注册失败可提示「用户名已占用」等与产品一致的信息。 |
| 日志脱敏 | 日志与异常栈不输出密码、完整 Token、refresh 串等（对齐 `shared.security`）。 |

### 2.2 MVP 认证模型建议

- **会话型（推荐与 config 一致）**：登录成功后建立服务端 Session（Redis 存储），Cookie 仅存 Session ID；**会话过期**后需重新登录（产品 §6.5）。
- **接口鉴权**：未登录访问需鉴权接口 → `401`，`code` 使用 `AUTH_TOKEN_EXPIRED` / `AUTH_UNAUTHORIZED` 等与 `shared.error_codes` 一致。
- **公开只读接口**：会议室列表、指定日期的占用/空闲视图可对 **访客** 开放（产品策略 A）；**创建/取消预约、我的预约** 必须登录。
- **「记住我」**：若产品启用，仅延长 **刷新令牌 / Session TTL** 体验，**不**放宽安全存储规则。

### 2.3 账号能力边界（MVP）

- 注册、登录、退出；**忘记密码**：线下/管理员（产品 §11.3），后端可不实现自助重置或仅占位接口。
- 密码强度：最小长度与复杂度在 API 层校验，与产品 §6.2 一致。

## 3. API 设计

### 3.1 通用约定（对齐 `rules.api`）

| 项 | 约定 |
|----|------|
| 基础路径 | `/v1/` 版本前缀；资源名 **复数**：`/v1/rooms`、`/v1/bookings` |
| Content-Type | `application/json` |
| 统一响应 | `{ success, code, message, data }`；`success: false` 时 `code` 为错误码，`message` 为对用户可读文案 |
| 请求头 | `X-Request-ID`（UUID）；关键写操作 `Idempotency-Key`（创建预约等）；Cookie 会话下变更类请求按需 **`X-CSRF-Token`**（与 `openapi.yaml` 一致）；认证：`Cookie` 或 `Authorization: Bearer` |
| 响应头 | 回传 `X-Request-ID`；限流时返回 `Retry-After`、`X-RateLimit-*`（见 §9） |
| 分页 | Query：`page`（默认 0）、`size`（默认 10）；响应：`{ page, size, total, items }` |
| 排序 | `sort=field,asc|desc`（如我的预约：`sort=startAt,desc`） |

### 3.2 错误码与 HTTP 映射（对齐 `shared.error_codes` + `rules.api`）

| HTTP | 典型 code | 场景 |
|------|-----------|------|
| 401 | `AUTH_TOKEN_EXPIRED`、`AUTH_UNAUTHORIZED` | 未登录、会话过期 |
| 403 | `PERMISSION_DENIED` | 越权（如取消他人预约） |
| 404 | `ROOM_NOT_FOUND`、`BOOKING_NOT_FOUND`、`RESOURCE_NOT_FOUND` | 会议室/预约不存在 |
| 409 | `USER_USERNAME_CONFLICT` | 注册时用户名已占用 |
| 409 | `BOOKING_CONFLICT_ROOM` | 会议室时段重叠（`data` 可为空对象，见 OpenAPI） |
| 409 | `BOOKING_CONFLICT_USER` | 用户同时段已约其他会议室；**`data.conflictingRoom` 必须含 `id`、`name`**（产品文案依赖） |
| 422 | `VALIDATION_FAILED` | 参数、跨日、过去时间、超 4 小时等 |
| 429 | `RATE_LIMIT_EXCEEDED` | 限流（**登录接口须单列更严策略**，见 §9.1） |
| 500 | `SYSTEM_*` | 服务器异常，消息对用户友好且不暴露内部 |

模块前缀与枚举以 **`openspec/config.yaml`** 与 **`openapi.yaml`** 为准：`AUTH_*`、`USER_*`、`ROOM_*`、`BOOKING_*`、`SYSTEM_*`。

### 3.3 资源与端点（与 `openapi.yaml` 对齐清单）

> 字段级契约、示例与错误体以 **`openspec/specs/openapi.yaml`** 为准。

| 方法 | 路径 | 鉴权 | 说明 |
|------|------|------|------|
| GET | `/v1/auth/password-params` | 无 | 下发 **`pepper`、`formulaVersion`**；客户端据此计算 **`passwordPrehash`** |
| POST | `/v1/auth/register` | 无 | 注册；请求体 **`username`、`passwordPrehash`**（契约公式），可选 **`displayName`**；冲突 **409 / `USER_USERNAME_CONFLICT`** |
| POST | `/v1/auth/login` | 无 | 登录，建 Session；**须配置严于普通接口的限流**（§9.1） |
| POST | `/v1/auth/logout` | 已登录 | 退出；响应 **200 + envelope**（见 OpenAPI） |
| GET | `/v1/rooms` | 可选 | 列表；**`capacityGte`**；**`amenity` 重复 query key** 多选（`amenity=a&amenity=b`） |
| GET | `/v1/rooms/{roomId}` | 可选 | 详情 |
| GET | `/v1/rooms/{roomId}/calendar` | 可选 | **必填 Query**：**`date=YYYY-MM-DD`**（业务日）；**可选 `timeZone`**（默认 **`Asia/Shanghai`**）。响应 **`data.items[]`** 每条仅 **`startAt`、`endAt`**（**禁止**他人 **`title`、`userId`**），产品 §9.2 |
| POST | `/v1/bookings` | 必填 | 创建预约；请求体 **`roomId`、`startAt`、`endAt`、`title`**；**必须**头部 **`Idempotency-Key`** |
| GET | `/v1/bookings/mine` | 必填 | 我的预约；筛选 **`roomId`、`dateFrom`、`dateTo`**；分页 **`page`/`size`** |
| POST | `/v1/bookings/{bookingId}/cancel` | 必填 | 取消本人未开始预约 |

**隐私**：访客可见的日历/占用 DTO **禁止**包含其他用户的 **`title`、`userId`、邮箱、显示名**；仅本人「我的预约」接口返回 **`title`** 等完整字段。

### 3.4 幂等与重试

- **创建预约**：客户端在「确认」重试时携带相同 `Idempotency-Key`，服务端在 TTL 内（如 24h）返回同一业务结果，避免重复落库。
- 与产品 §11.1「网络抖动」表现一致。

## 4. 数据库设计

### 4.1 命名与类型（对齐 `rules.backend` MySQL 建模）

- 主键：单体可用 **BIGINT 自增**；若未来分库再迁 UUID。
- 时间：统一 **`datetime(3)`** 或 **`timestamp(3)`**（与 MySQL 时区配置一致），存 **UTC** 或 **固定业务时区（如 Asia/Shanghai）** 二选一并全链路统一（见 §6）。
- 字符集：`utf8mb4`；排序 `utf8mb4_unicode_ci`（或项目统一规则）。

### 4.2 核心表（评审级）

**`user`（用户）**

| 字段 | 说明 |
|------|------|
| id | PK |
| username | UNIQUE，NOT NULL |
| password_hash | BCrypt/Argon2 |
| display_name | 可选 |
| created_at / updated_at | 审计 |

**`meeting_room`（会议室，预置）**

| 字段 | 说明 |
|------|------|
| id | PK |
| name, location | 展示 |
| capacity | INT |
| amenities | JSON 或关联表（设施字典延后时可 JSON） |
| created_at | 可选 |

**`booking`（预约）**

| 字段 | 说明 |
|------|------|
| id | PK |
| room_id | FK → meeting_room |
| user_id | FK → user |
| title | 会议主题 |
| start_at, end_at | NOT NULL；**约束 end_at > start_at** |
| status | `ACTIVE` / `CANCELLED`（软删取消，便于审计） |
| version | 可选，乐观锁（见 §5） |
| created_at / updated_at | |

### 4.3 索引与约束（支撑规则与查询）

- `booking(room_id, start_at, end_at)`：会议室维度时间范围查询。
- `booking(user_id, start_at)`：用户同时段冲突检测。
- **重叠排除**：MySQL 不原生支持 EXCLUDE，需在应用层 + 事务内校验；可选 **generated 列 + 函数索引** 辅助，详见 §5。
- 过滤：`meeting_room(capacity)`；设施筛选视存储方案加索引或应用层。
- 变更：**Flyway/Liquibase** Migration，可回滚。

### 4.4 业务约束与数据层护栏

- 同一会议室时段不重叠：**事务内 SELECT … FOR UPDATE 或唯一约束思路**（§5）。
- 同一用户同时段仅一间：**同上**。
- **跨日**：产品建议 MVP 不支持 → 可在应用层校验 `DATE(start_at) = DATE(end_at)`，违反返回 `VALIDATION_FAILED`。

## 5. 并发处理（冲突、锁、空表防护）

### 5.1 并发场景（产品 §11.1）

两人同时抢占同一空档：**一方成功，另一方冲突错误码**（会议室占用）；需保证 **无重复插入**。

### 5.2 推荐策略（组合）

1. **事务隔离**：默认 Spring `@Transactional`；预约创建使用 **`READ COMMITTED` 或 `REPEATABLE READ`**（MySQL InnoDB RR + 间隙锁可对范围加锁，注意死锁重试）。
2. **悲观锁**：在事务内按 **固定顺序** 锁定资源，例如：
   - `SELECT * FROM booking WHERE room_id=? AND status=ACTIVE AND … FOR UPDATE`（或使用 **next-key** 锁住时间区间相关行）。
   - 对用户维度同样查询未结束预约是否时间重叠。
3. **顺序一致性**：对 `(room_id, user_id)` 加锁顺序固定（先 room 后 user），降低死锁。
4. **乐观锁**：`booking.version` 更新时校验，适用于取消、改状态；创建路径仍以悲观锁或唯一约束为主。
5. **数据库约束辅助（可选）**：若业务可接受，可用 **重叠检测的中间表示**（例如将授权时段离散化为槽位表）简化唯一性；MVP 常用 **应用层重叠算法 + 锁**。

### 5.3 重叠判定（单一会议室）

有效预约：`status = ACTIVE`，区间 `[start_at, end_at)`。新业务 `(s,e)` 与已有 `(s_i,e_i)` 冲突当且仅当 **`s < e_i AND e > s_i`**。

用户维度：对所有 **ACTIVE** 且与自己时间重叠的 booking，若存在 `room_id ≠ 当前 room_id` → `BOOKING_CONFLICT_USER`。

### 5.4 「空表」与极端数据

- **会议室预置**：列表为空属数据异常 → 接口返回空数组 + 日志告警；产品 §9.1「联系管理员」。
- **某日无预约**：日历查询正常返回全空闲，无需特殊分支；缓存需区分 **空列表** 与 **未加载**（见 §8 穿透）。
- **大数据量日历**：按日查询 + 索引，避免全表扫。

### 5.5 取消与并发

取消仅允许 **当前时间 < start_at**（产品 §11.5）。更新时 `WHERE id=? AND user_id=? AND status=ACTIVE AND start_at > NOW()`，**匹配行数 0** 时返回业务错误（已开始/已结束/已取消），避免并发下误取消。

## 6. 时间处理（服务器/客户端与 Java API）

### 6.1 单一事实来源

- **业务判定以服务器当前时间为准**（「过去/未来」「是否可取消」「进行中」）。
- 客户端传的 `startAt/endAt` 必须为 **ISO-8601**（含偏移或 Z），服务端解析后规范到统一时区存储。

### 6.2 Java API 建议（JDK 17）

| 用途 | 建议 |
|------|------|
| 领域模型与持久化边界 | `Instant`（UTC）或数据库驱动与 JDBC 映射约定一致 |
| 面向区间计算、用户展示 | `ZonedDateTime`（ZoneId 如 `Asia/Shanghai`） |
| **禁止** | 混用 `java.util.Date` 作为新代码主路径 |
| JDBC | `java.time` 与 MyBatis TypeHandler 显式配置；全表时间精度一致 |

### 6.3 与产品规则对齐

- **不能预约过去**：`startAt` 须 `> now`（可配置容忍时钟 skew 数秒）。
- **单次 ≤ 4 小时**：`Duration.between(start, end) ≤ 4h`。
- **跨日**：产品建议不支持 → `toLocalDate()` 相等校验。

### 6.4 客户端时钟偏差

- 短容忍窗口（如 30s）仅缓解显示误差；**权威时间始终服务端**。

## 7. 事务管理

### 7.1 边界

- **创建预约、取消预约**：单 Service 方法内 **`@Transactional(rollbackFor = Exception.class)`**，读-判-写同事务完成。
- **只读列表/日历**：只读事务或不开事务；避免在长事务中持锁读无关表。

### 7.2 传播与隔离

- 默认 `REQUIRED`；内部查询与插入同一事务。
- 隔离级别：与 DBA 确认默认；高冲突场景可考虑 **乐观重试**（捕获死锁/锁等待超时后有限次重试，记录 `X-Request-ID`）。

### 7.3 与缓存一致

- 写路径：先 **提交 DB**，再 **删/更新 Redis 相关 key**（或延迟双删策略按项目缓存设计）；读路径以 DB 为准修复缓存（见 §8）。

## 8. Redis：热点数据与穿透/击穿/雪崩

### 8.1 Key 命名（对齐 `rules.backend` Redis）

格式：`{业务域}:{子模块}:{标识}`，示例：

- `meetingroom:room:{roomId}:calendar:{date}`：某日该会议室占用摘要（TTL 短，如 60s）。
- `meetingroom:rooms:list:{filterHash}`：列表过滤结果（可选，TTL 5–60s）。
- `auth:session:{sessionId}`：会话（TTL 与产品会话时长一致，如 30min，可滑动续期）。

**必须设置 TTL**；Session 类与「接口缓存」类分别设合理过期（config 示例：Session 30min，接口缓存 5–60s）。

### 8.2 热点数据

- **会议室列表、热门日期的日历**：短 TTL + 本地缓存（Caffeine）可选；监控大 key 与热点 key。

### 8.3 缓存穿透

- 对 **不存在的 roomId**：DB miss 后可缓存 **空占位**（短 TTL），避免反复打 DB；与 **业务 404** 语义一致。
- **非法日期/越权 ID**：校验前置，不进缓存。

### 8.4 缓存击穿

- 极高并发读同一过期 key：使用 **互斥重建**（单飞）、或 **逻辑过期**（后台异步刷新）、或热点 key **永不过期 + 异步更新**策略择一实现。

### 8.5 缓存雪崩

- TTL **加随机抖动**（如 60±10s）；多级缓存；依赖 **熔断/限流** 保底；核心读路径 **可降级直查 DB**（需连接池与 DB 扛得住）。

### 8.6 与「空表」

- 空列表允许缓存「空数组」占位，防止穿透式反复查询（短 TTL）。

## 9. 接口限流与其它生产化要点

### 9.1 限流（对齐 `rules.backend`）

- **组件**：**Resilience4j** 或 **Sentinel**（与 Spring Boot 3 集成）。
- **维度**：IP、用户 ID、接口（如 **`POST /v1/bookings`** 写路径更严）、全局限流。
- **`POST /v1/auth/login`（强制）**：须配置 **严于只读接口** 的阈值（推荐：**同一 IP** 每分钟 **≤ 5** 次，可按 **用户名** 叠加维度）；与 **`openapi.yaml`** 描述一致，防止口令暴力尝试。
- **响应**：HTTP **429**，`code: RATE_LIMIT_EXCEEDED`，**`Retry-After`**（秒）；响应头 **`X-RateLimit-Limit/Remaining/Reset`**（若实现）。
- **友好文案**：与产品 §11.4「访问过于频繁」一致。

### 9.2 其它（config 摘要）

- **连接池**：HikariCP 参数按环境调优（如 `maximum-pool-size=20`）。
- **健康检查**：Actuator `/health`；优雅停机 `server.shutdown=graceful`。
- **可观测性**：Micrometer + Prometheus；Trace ID 与 `X-Request-ID` 对齐。

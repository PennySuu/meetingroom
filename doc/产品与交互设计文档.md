## 2. 背景与产品目标

### 2.1 问题陈述（与需求文档一致）

企业内部多间会议室依赖即时通讯「喊一声」占位，导致：

- 到场后发现已被占用，双方认知不一致；
- 同一人同时占用多间会议室，他人无房可用；
- 不清楚空闲时段，需逐个询问或到现场查看。

### 2.2 产品目标（MVP）

1. **可感知空闲**：一眼看到会议室信息与某日可预约的空档。  
2. **可信赖预约**：同一会议室时段不重叠；同一用户在相同时段只占用一间会议室。  
3. **可追溯记录**：用户能查看自己的预约并按条件筛选。  
4. **可控访问**：仅 **已注册且已登录** 的用户可 **发起预约、取消自己的预约** 并管理「我的预约」；访客仅可浏览列表与日历。

### 2.3 成功指标（建议，非技术）

- 用户能在 **3 分钟内** 完成「选会议室 → 选时段 → 填写主题 → 预约成功」主路径；  
- 冲突与校验失败时，用户能 **理解原因** 并 **一次修正**；  
- 核心列表与日历在常见网络环境下 **可流畅浏览**（具体性能指标由技术方案承接）。

## 3. 目标用户与典型场景

| 角色 | 描述 | MVP 范围 |
|------|------|----------|
| **普通员工** | 需要开会、预定会议室 | 注册/登录、浏览会议室、创建预约、**取消预约**、查看「我的预约」 |
| **访客/未登录用户** | 想了解是否有会议室信息 | **策略 A（已定）**：可浏览 **会议室列表与预约日历**；**发起预约（提交）前必须登录/注册** |

### 3.1 典型场景（细化）

| 场景 ID | 场景描述 | 用户期望 |
|---------|----------|----------|
| S1 | 明天下午部门例会，需要 10 人、投影 | 按容量与设施筛选 → 进入日历 → 选连续空闲时段 → 填写主题 → 成功 |
| S2 | 临时 1 小时讨论，越快越好 | 默认今天 → 看最短可用空档 → 快速下单（仍须满足时长与冲突规则） |
| S3 | 想改期，但怕和别的会撞 | **MVP**：无独立「改期」入口时，先 **取消预约**（见 §9.3）再在日历上重新预约；**会议已开始则不可取消**，需另约时段或会议室 |
| S4 | 提交时提示「与已有预约冲突」 | 明确是 **会议室冲突** 还是 **本人已占用其他会议室** → 给出可操作建议（换时段/换会议室） |
| S5 | 新员工首次使用 | 完成注册 → 登录 → 与 S1 相同 |

## 4. MVP 范围与延后项

### 4.1 MVP 必须包含（与需求文档对齐 + 本期新增账号）

| 模块 | MVP 内容 |
|------|-----------|
| 账号 | 用户 **注册**、**登录**、**退出登录**；会话过期后需重新登录 **【补充：原文未含，本期必做】** |
| 会议室 | 列表展示名称、位置、容纳人数、设施标签；按 **容量**、**设施** 筛选 |
| 预约 | 选会议室 → 日历/时间视图 → 选开始/结束时间 → 填写 **会议主题** → 提交；**取消本人预约**（入口以「我的预约」为主） |
| 校验 | 会议室时段不重叠；**同一用户同一时段仅能预约一间会议室**；**单次时长上限（如 ≤4 小时）**；**不可选过去时间** |
| 我的预约 | 列表展示；按 **会议室**、**日期范围** 筛选；**分页**；支持 **取消预约**（本期） |
| 数据 | 会议室 **预置**，用户不能在线创建会议室 **【与原文一致】** |

### 4.2 明确延后（非 MVP）

以下**不写入本期验收**，避免范围膨胀：

- 会议室管理后台、标签/设施字典在线配置；
- **修改预约**（在不取消的情况下直接改时间/主题）；**签到释放**；
- 周期性会议、代办邀请、与会人管理；
- 与日历（Outlook/Google）、IM、邮件的深度集成；
- 消息通知（站内信、邮件、企业微信）；
- 组织结构、会议室权限到部门级、审批流；
- 数据统计大屏、使用率报表；
- 多租户、品牌化定制。

## 5. 功能架构（信息架构）

从产品视角分为四层，便于对齐页面与权限：

```
访客（未登录）
  ├── 会议室列表（浏览、筛选）
  └── 预约日历（浏览空闲/占用；点击「确认预约」→ 登录/注册）

注册用户（登录后）
  ├── 会议室列表（筛选 → 进入预约）
  ├── 预约日历（选时段 + 填写主题 → 提交）
  └── 我的预约（筛选 + 分页 + 取消预约）

账号（登录态）
  ├── 注册 / 登录 / 退出
  └── 会话失效 → 拦截需登录操作 → 引导登录
```

**说明**：访客策略见 **§7（已定：方案 A）**。

## 6. 账号体系：注册、登录与退出（本期必含）

### 6.1 设计原则

- **低摩擦**：字段尽量少，错误提示可读、可修正；  
- **安全感知**：密码强度要求、登录失败反馈不泄露账号是否存在（**对外文案**层面）**【与 openspec 安全理念一致，产品侧不规定算法】**；  
- **一致性**：所有需身份的操作依赖统一登录态，避免「半截可用」造成误操作。

### 6.2 注册

| 元素 | 说明 |
|------|------|
| **入口** | 登录页的「注册」链接；未登录访问需登录页面时跳转注册可选 |
| **推荐字段** | **用户名**（唯一）、**密码**、**确认密码**；可选 **显示名称**（用于「我的预约」展示）**【补充】** |
| **校验（产品规则）** | 用户名：非空、长度与字符限制（禁止空格等，具体由校验规则文档统一）；密码：最小长度、复杂度（数字+字母等）；两次密码一致 |
| **成功后** | 自动登录并进入 **会议室列表**（或上次访问页，若可控） |

### 6.3 登录

| 元素 | 说明 |
|------|------|
| **入口** | 全局入口；访问需登录资源时弹窗或整页引导登录 |
| **字段** | 用户名 + 密码；可选「记住我」（若做，仅影响会话时长体验，**不**在界面存储密码）**【openspec：凭证安全由实现保证】** |
| **失败后** | 通用文案：登录失败，请检查用户名或密码；**不明确提示**「用户不存在」或「密码错误」**【补充：防枚举，产品文案要求】** |
| **成功后** | 进入默认首页（建议会议室列表）或 **重定向回** 用户原本要去的页（含预约日历深链）**【补充：提升深链体验】** |

### 6.4 退出登录

- 入口：页头用户菜单「退出」。  
- 退出后：清理登录态展示，需登录的操作不可再执行；给出轻提示「已退出」。

### 6.5 会话过期 / 未登录拦截

| 情况 | 交互 |
|------|------|
| 会话过期 | 用户继续操作时：提示「登录已过期，请重新登录」，保留当前页面路径以便登录后返回 **【补充】** |
| 直接访问预约页 | 跳转登录页，登录成功后回到预约日历 |

## 7. 访问策略（已定）

需求原文未规定「未登录能否看会议室」。**本期固定采用方案 A：**

| 已定方案 | 描述 |
|----------|------|
| **A** | 未登录用户可浏览 **会议室列表** 与 **预约日历**（查看空闲/占用）；点击 **提交预约**（或等价主操作）时 **必须登录或注册**，完成后可继续预约流程（建议回到原会议室日历并保留意图）**【补充】** |

未登录用户在日历上的 **选时、填表** 可与登录后一致至「提交」一步，也可在点击提交时再唤起登录——具体交互二选一，但须保证：**未登录无法产生有效预约**。

## 8. 核心用户流程

### 8.1 主路径：首次预约（已注册）

1. 打开 **会议室列表** → 可选筛选 → 选定一间会议室 → 进入 **预约日历**。  
2. 选择日期（默认：**今天**；可切到未来日期）**【补充：默认日期】**。  
3. 在时间表上选取 **开始时间** 与 **结束时间**（或选空档模板，由交互实现二选一）。  
4. 填写 **会议主题**（必填）。  
5. 点击「确认预约」→ 系统校验 → 成功则进入成功反馈，并可从成功页跳转到「我的预约」或返回日历。

### 8.2 主路径：从「我的预约」回溯

1. 进入「我的预约」→ 查看列表 → 可跳转至对应会议室日历（便于复用同一间）**【补充：跳转视实现，属体验增强】**。

### 8.3 注册到首次预约

注册成功 → 会议室列表 → 与 8.1 相同。

### 8.4 访客浏览后预约（策略 A）

1. 未登录进入 **会议室列表 / 日历**（与登录用户一致的浏览能力）。  
2. 选择时段并填写主题后点击 **确认预约** → 跳转 **登录或注册**。  
3. 完成身份后回到 **原会议室日历**（或预约弹层），用户可再次确认并提交 **【补充：避免丢上下文】**。  

### 8.5 取消预约（本期）

1. 在 **我的预约** 中，仅对 **尚未开始**（当前时间仍早于开始时间）的预约可点击 **取消预约**；**进行中、已结束** 的预约 **不可取消**（见 §9.3、§11.5）。  
2. 二次确认（文案说明释放时段、不可自动恢复）。  
3. 成功后：该条状态更新为已取消（或从列表移除，二选一并全站一致）；会议室日历对应时段 **恢复为可约**；若用户停留在该会议室日历，应刷新占用显示。  

**「改期」**：本期通过 **取消 + 重新预约** 完成，不提供单独改期表单 **【补充】**。

## 9. 页面级交互说明

### 9.1 会议室列表页

| 区域 | 内容与交互 |
|------|------------|
| 页头 | 产品名；已登录展示用户入口（我的预约、退出）；未登录展示「登录 / 注册」 |
| 筛选区 | **容量**：如 ≥N 人；**设施**：多选标签（投影、白板、视频会议等），**空选**表示不限 **【与需求一致】** |
| 列表卡片/行 | **名称**、**位置**、**容纳人数**、**设施标签**；每项有主操作「去预约」进入该会议室日历 |
| 空状态 | 无会议室：提示联系管理员（因数据预置，一般仅开发/数据异常时出现） |
| 筛选无结果 | 提示「没有符合条件的会议室，请放宽筛选」**【补充】** |

### 9.2 预约日历页

| 区域 | 内容与交互 |
|------|------------|
| 上下文 | 显示当前会议室 **名称 + 位置**（强化「约的是哪一间」）**【补充】** |
| 日期 | 日期切换；**禁止选过去日期**（或选后无法提交并提示）**【与需求：不能预约过去一致】** |
| 时间格 | **已占用**与**空闲**视觉区分；**已占用时段一律不展示他人会议主题**，仅展示 **「已占用」**（或等价中性文案），以保护隐私 **【已定】** |
| 新建预约 | 选时段 → 打开侧栏/弹窗：**开始、结束**（或时长）、**会议主题**；展示 **单次时长上限** 提示 **【需求：≤4 小时】** |
| 「我的预约」入口 | 当前会议室相关的快捷入口或全局入口 |

**交互细节（补充）**：

- 结束时间必须 **晚于** 开始时间；跨度超过 4 小时立即提示并禁止提交。  
- 点击过去的时间格：无响应或 Toast「不能预约过去的时间」。  
- 跨越午休等：不需要特殊规则则按连续时间处理即可。

### 9.3 我的预约页

| 区域 | 内容与交互 |
|------|------------|
| 筛选 | **会议室**（下拉）、**日期范围**（起止）；「重置」**【与需求一致】** |
| 列表 | 每条：**会议室、日期、时间段、主题**（**本人预约可见主题**）；按开始时间倒序 **【补充：排序规则】** |
| 操作 | **取消预约**：仅对 **未开始** 的预约展示可用按钮；**进行中** 预约 **不提供取消**（按钮隐藏或禁用，辅助说明：「会议进行中，无法取消」）**【已定】**；**已结束** 同理不可取消。点击后 **二次确认**（见 §8.5） |
| 分页 | 上一页/下一页或页码；每页条数可选若成本高则固定 **【补充】** |
| 空状态 | 「暂无预约」，引导去会议室列表 |

## 10. 业务规则（产品表述）

下列与 `需求文档.md` 一致处不再赘述编号，此处强调**对用户可见的表述**：

| 规则 | 用户可见说明示例 |
|------|------------------|
| 会议室数据预置 | 用户界面不提供「新建会议室」 |
| 预约须 **开始 & 结束** | 表单两处必选；时长由二者计算 |
| 同一会议室时段不重叠 | 「该时段已被占用，请更换时间或其他会议室」 |
| 同一用户同时段只能约一间 | 「该时段您已预约其他会议室：[会议室名称]，请先调整」——**须使用 API 返回的冲突会议室名称**（**`409` / `BOOKING_CONFLICT_USER`，`data.conflictingRoom.name`**，见 **`openspec/specs/openapi.yaml`**） |
| 单次 ≤ 4 小时 | 「单次预约最长 4 小时，请缩短时段或拆分会议」 |
| 不可预约过去 | 「开始时间不能早于当前时间」 |
| 取消预约（本期） | 用户仅可取消 **本人** 且 **尚未开始** 的预约；**进行中不可取消**；成功后时段释放（见 §11.5） |

## 11. 边界场景与异常流程

### 11.1 并发与最后一秒抢占

| 场景 | 期望体验 |
|------|----------|
| 两人同时选同一空档提交 | 一方成功，另一方收到 **冲突提示**（会议室已被占用），日历刷新展示最新占用 |
| 提交瞬间网络抖动 | 加载态防重复提交；失败后允许重试；**幂等可由技术侧保障，产品表现为「请勿重复点击」** |

### 11.2 跨日预约

| 场景 | MVP 建议 |
|------|----------|
| 会议跨越 0 点 | **可不支持**：提示「单次预约不能跨自然日」，要求拆分 **【补充：需求未写，为避免复杂度】** |

### 11.3 用户边界

| 场景 | 期望体验 |
|------|----------|
| 忘记密码 | **MVP**：页面文案「请联系管理员重置」或线下流程 **【补充】** |
| 同一浏览器多账号 | 以后登录为准；退出再登录切换 |

### 11.5 取消预约的边界

**状态划分（产品口径）**：**尚未开始** = 当前时间早于开始时间；**进行中** = 已到开始时间且早于结束时间；**已结束** = 已过结束时间。**到达开始时刻起即视为进行中**，不可再取消。

| 场景 | 期望体验 |
|------|----------|
| 取消 **已结束** 的预约 | 不提供取消或按钮禁用；若误操作请求，提示「该预约已结束」**【补充】** |
| 取消 **进行中** 的预约 | **不可取消（已定）**：不提供取消入口或 **禁用**，说明「会议进行中，无法取消」；若接口被恶意调用，返回业务错误并提示同左 **【补充】** |
| 距开始很近 | 是否限制临开场前 X 分钟不可取消——**本期可不设限**（若运营有要求再收紧）**【补充】** |
| 重复点击取消 | 加载态防重复；成功或失败后明确反馈 |
| 取消后日历 | 返回会议室日历时，该格应显示为空闲（或短暂刷新延迟后一致） |

### 11.4 异常与降级（用户可见）

| 场景 | 期望体验 |
|------|----------|
| 列表/日历加载失败 | 失败提示 + 「重试」按钮 |
| 服务器报错 | 「服务暂时不可用，请稍后重试」（与 openspec **错误提示友好性**一致，不暴露内部信息） |
| 限流（含登录保护） | 「访问过于频繁，请稍后再试」；对 **登录** 等敏感入口，前端宜根据 **`Retry-After`** 呈现冷却/倒计时（见 **`openapi.yaml`**、后端评审 §9.1） |

## 12. 非功能体验要求（产品层）

- **无障碍（力所能及）**：表单控件有标签；错误信息与输入关联；关键对比度达标 **【通用 UX】**。  
- **文案**：简短、指导性；按钮动词明确（「确认预约」「登录」）。  
- **隐私**：日历视图下 **不向他人展示会议主题**，仅展示占用事实（见 §9.2）；「我的预约」中本人可见自己的主题。  
- **审计**：不在本文展开；实现阶段遵循项目安全与日志规范 **【config 指向 SDD】**。
